# AI 团队方案总结

> 状态：需求与关键决策已确定，进入技术验证与实现设计阶段
> 更新时间：2026-10-22
> 当前范围：主管 Claude Code + 员工 pi agent；Windows 局域网多节点；暂无独立 UI

**已完成的会话验证**：本机 Claude Code 2.1.304 与 pi 1.3.0 均可通过固定 session id 在独立进程间恢复同一会话，两轮测试均能记住约定内容。详见第 9 节。

## 1. 项目目标

构建一个由主管 harness 驱动的 AI 团队系统：

- 用户直接在主管的 Claude Code 会话中管理员工、分配任务、查询结果，当前不提供独立 CLI、Web 或桌面 UI。
- 主管本身是 Claude Code harness，拥有持久会话和 MCP 管理工具，负责拆解目标、创建员工、分派与验收任务。
- 员工初期使用 pi agent，是绑定某台 Windows 节点、一个工作目录和一个持久会话的 harness 实例。
- 同一员工跨任务复用同一个会话；员工之间彼此隔离。
- 主管电脑可以关机；已经下发到节点的任务继续执行，结果持久化在节点本地，主管会话启动后可查询。
- 用户既可以明确指定员工，也可以只给出目标由主管自主分派。
- 未来可扩展员工端的 harness 类型（opencode、Claude Code 等），初期只实现 pi。

## 2. 核心概念

| 名称 | 定义 |
|---|---|
| 用户 | 与主管对话的人，可下达目标、显式指派任务、查询结果、作出后续决策 |
| 主管 | `supervisor` 角色的 Claude Code harness 实例，拥有持久会话和 MCP 团队管理工具；负责管理，不直接执行员工任务 |
| 员工 | `worker` 角色的 pi harness 实例，定义为 **harness 类型 + 所在节点 + 工作目录 + 持久会话** |
| 节点 | 一台运行员工 harness 的 Windows 电脑，同一局域网内可达 |
| 节点代理 | 运行在节点登录用户会话中的常驻程序，监听局域网端口，负责任务持久化、驱动 pi、维护会话、保存结果和事件日志 |
| 编排层 | 主管端的管理服务，向 Claude Code 暴露 MCP 工具，并主动连接节点代理、维护团队与任务状态 |
| 任务 | 最小执行单元，必须自包含：目标、约束、验收标准、必要上下文 |
| 结果报告 | 员工完成后返回的任务结果全文，是主管验收和用户查询的依据 |
| 事件日志 / Outbox | 节点端按顺序持久化任务结果，在主管端确认接收前一直保留 |
| 主管上线 | 主管会话启动，主管 harness 可以调用 MCP 工具并查询结果 |

角色差异：

| 维度 | 主管 | 员工 |
|---|---|---|
| Harness | Claude Code | pi（初期） |
| 角色提示词 | 拆解、分派、验收、维护团队 | 在指定工作目录内完成具体任务 |
| 工具权限 | MCP 团队与任务管理工具 | 常规 coding 工具，不含团队管理工具 |
| 工作目录 | 团队根目录或配置目录 | 各自绑定的项目目录 |
| 会话 | 主管端持久会话 | 节点端持久会话 |

## 3. 系统架构

```
┌────────────────────────── 主管电脑（可关机） ──────────────────────────┐
│  用户 ⇄ 主管 Claude Code 会话 ⇄ MCP 管理工具 ⇄ 编排层                   │
│                                               ├─ SQLite：团队 / 任务索引 │
│                                               └─ 主动连接节点（局域网）   │
└──────────────────────────────┬──────────────────────────────────────────┘
                               │ 主管端主动连接节点代理
         ┌─────────────────────┴─────────────────────┐
┌────────▼─────────────┐                  ┌──────────▼───────────┐
│ Windows 节点 A        │                  │ Windows 节点 B        │
│ 节点代理（监听端口）   │                  │ 节点代理（监听端口）   │
│ pi 会话 / 任务执行     │                  │ pi 会话 / 任务执行     │
│ SQLite 事件日志/Outbox │                  │ SQLite 事件日志/Outbox │
└───────────────────────┘                  └───────────────────────┘
```

### 3.1 职责划分

| 端 | 负责 | 不负责 |
|---|---|---|
| 主管端 | 主管会话、MCP 管理工具、任务派发、团队状态、结果查询与汇总 | 执行员工任务、读取员工节点文件 |
| 节点端 | 任务接收与持久化、pi 执行、会话维护、结果保存与补报 | 团队决策、跨节点调度 |

### 3.2 已确定的部署与技术选型

- **主管 harness**：Claude Code。
- **员工 harness**：pi agent。
- **主管工具注入**：MCP。编排层向主管的 Claude Code 会话暴露团队管理工具。
- **节点通信**：节点代理监听局域网端口，主管端主动连接节点；“主管上线”不依赖节点主动上报。
- **持久化**：主管端与节点端均使用 SQLite；节点结果以有序事件日志/Outbox 保存。
- **界面**：暂无独立产品界面，所有管理与分配都在主管 Claude Code 会话中进行。
- **版本**：Claude Code、pi 以及后续接入的 opencode 均使用最新版本并锁定；升级流程后续确定。
- **运维**：节点代理需要打包、随用户登录启动；需要凭据管理和日志管理。
- **安全**：具体方案（鉴权、传输加密、审计、令牌管理）后续确定。

## 4. 关键机制

### 4.1 会话连续性与全文注入

- **员工会话**：同一员工的后续任务始终使用同一个 pi 会话，保留历史上下文和工作记忆。节点代理按员工保存 session id。
- **主管会话**：跨用户请求保持同一个 Claude Code 会话；主管会话启动即视为上线。
- **结果全文注入**：用户查询任务结果时，主管通过 MCP 工具获取员工返回的任务结果**全文**并注入主管上下文，不做摘要替代。“全文”指员工返回的完整任务结果。
- **外部存储**：完整结果同时保存在节点事件日志和主管端数据库中，不依赖上下文留存。
- **上下文增长**：当前接受全文注入带来的主管上下文增长；压缩或摘要策略后续再定。
- **串行执行**：一个员工同一时间只执行一个任务，后续任务排队，避免同一会话被并发写入。

### 4.2 任务指派双入口

两种入口都发生在主管 Claude Code 会话内：

| 入口 | 决策方式 | 行为 |
|---|---|---|
| 对话入口 | 用户明确指定员工时由用户决定；用户只给目标时由主管自主决定 | 主管解析意图；指代不清必须先确认，不能猜测 |
| 显式入口 | 用户使用固定格式的指派指令，携带明确员工标识和任务内容 | 主管必须按原参数调用 MCP `assign_task`，不得擅自改派 |

共同规则：

- 两个入口生成同一种任务对象，并记录来源：`assignment_source = user | supervisor`。
- 用户明确指定员工后，主管不得擅自替换员工。
- 显式入口执行后，也要把“已向某员工派发任务”记录为主管会话事件，保证主管上下文与团队事实一致。
- 员工在线但正忙时，任务进入该员工的队列。
- 员工所在节点离线时，立即报错，不创建任务、不排队、不等待，由用户决定等待、换人或新建员工。
- 当前没有独立 UI，显式入口是会话内指令；若后续需要更强确定性，再增加专门入口。

### 4.3 离线执行与结果查询

1. 用户或主管发起任务，主管端把任务提交给员工所在节点。
2. 节点代理必须先持久化任务，再返回接受确认；未持久化的任务不得视为已派发。
3. 任务在该员工的 pi 会话中执行。主管端离线不影响已接收任务继续运行。
4. 任务结束（成功、失败、需要澄清、取消或中断）后，结果报告按顺序写入节点 SQLite 事件日志/Outbox。
5. 主管会话启动后，用户可主动查询任务结果；主管通过 MCP 工具拉取未确认结果，把完整结果注入主管上下文，并标记已接收。
6. 系统不主动把所有结果推入主管会话；结果保留在节点和主管端数据库中，等待用户查询。

约束：

- 结果投递采用“至少一次”，以 `task_id` 和事件序号去重，保证主管端崩溃重连后不丢结果、不重复处理。
- Outbox 中的结果在主管端确认前一直保留。
- 尚未成功下发到节点的任务，在主管离线期间不会执行。
- 任务必须自包含。员工需要澄清时应以 `needs_input` 结束任务，不能挂起等待主管上线。
- 主管离线期间不能派发新任务。

### 4.4 任务状态与控制

```
queued ──▶ running ──▶ succeeded
             │
             ├──▶ failed
             ├──▶ needs_input
             ├──▶ interrupted
             └──▶ canceled
```

- `queued`：员工在线且正忙，任务在其队列中等待；节点离线不会产生 `queued`。
- `failed`：执行失败，按失败结果上报；超时也记为 `failed`，原因标记为 `timeout`。
- `needs_input`：员工需要用户或主管澄清；该任务结束，后续回答作为新任务续接同一会话。
- `interrupted`：节点注销、睡眠、重启、节点代理退出等导致执行中断；恢复后补报，不自动续跑。
- `canceled`：用户或主管显式取消；节点代理终止 pi 进程树并记录取消结果。
- **超时**：默认不启用，按任务配置。
- **不自动重试**：重试属于新建任务，可以复用同一员工会话，原任务记录保留。
- **验收与改派**：拒绝或改派视为新建任务；原任务记录不改写；新任务携带前序任务结果报告作为上下文。
- **目录隔离**：同一节点允许多个员工，但禁止两个员工共用同一个工作目录。

## 5. 功能需求

| 编号 | 需求 | 关键约束 |
|---|---|---|
| FR-01 | 团队管理 | 主管可创建员工，指定 pi harness、所在节点、工作目录；支持查看与停用；初期不支持删除或修改工作目录 |
| FR-02 | 双入口指派 | 会话内自然语言指派与固定格式显式指派；用户指定优先；节点离线立即报错 |
| FR-03 | 会话复用 | 同一员工跨任务复用同一 pi 会话；一次只执行一个任务，后续任务排队 |
| FR-04 | 任务控制 | 支持显式取消；超时默认不启用、按任务配置；失败不自动重试 |
| FR-05 | 离线执行与结果查询 | 已下发任务在主管离线时继续执行；结果本地持久化；主管会话启动后用户可查询并注入全文 |
| FR-06 | 验收与后续 | 员工提交完整结果报告；主管验收；拒绝或改派生成携带前序报告的新任务 |
| FR-07 | 状态可观测 | 可查看员工列表、节点状态、员工停用状态、任务状态、任务历史、结果与错误 |
| FR-08 | 权限边界 | 主管不能读取员工节点文件；员工只能操作自己绑定的工作目录；员工无团队管理工具 |

### 员工生命周期

- 当前只支持：创建、查看、停用。
- 停用后不再接受新任务；执行中的任务可由用户或主管显式取消。
- 不支持删除员工、修改员工工作目录或更换节点。

### 结果报告结构

主管没有读取员工节点文件的能力，结果报告是唯一验收依据。员工返回的任务结果全文至少包含：

- 执行结论与是否满足验收标准；
- 改动文件清单；
- 验证或测试结果；
- 遗留问题与风险；
- 需要用户或主管决策的事项；
- 必要时附关键文件内容或 diff 摘录，由员工主动提交。

## 6. 权限与安全边界

- **主管**：只有 MCP 团队与任务管理能力；不提供读取员工节点文件的工具或通道。
- **员工**：只操作自己绑定的工作目录；不获得团队管理工具，不能自行创建员工或给其他员工派任务。
- **节点代理**：只接受主管端的管理请求；限制员工工作目录范围；记录任务与操作日志。
- **局域网**：节点代理只监听局域网，不暴露公网；具体鉴权方式后续确定。
- **凭据与日志**：节点代理负责管理 pi 的凭据和运行日志；具体轮换、权限和保留策略后续确定。

## 7. 运行边界

### 7.1 运行前提

- 所有节点位于同一局域网。
- 员工机保持开机、保持登录、保持唤醒；锁屏可以继续执行。
- 节点代理在登录用户会话中运行，随登录启动，不做 Windows 服务。
- 注销、睡眠、重启会中断执行中的任务，恢复后按 `interrupted` 补报，不自动恢复执行。
- 主管电脑可随时关机；主管恢复并启动会话后可查询结果。
- 主管离线期间已下发任务继续执行的前提是员工节点满足上述条件。

### 7.2 当前不做

- 独立 CLI、Web、桌面 UI；
- Windows 服务化、无登录无人值守运行；
- 跨网络 / 公网访问；
- 任务失败自动重试；
- 主管读取员工节点文件；
- 多主管与权限分级；
- 删除员工、修改员工工作目录；
- 员工端接入 pi 之外的 harness（后续扩展）。

## 8. 验收场景

1. 主管创建 pi 员工，分别绑定不同节点和工作目录；主管能通过 MCP 工具查看员工并派发任务。
2. 员工完成第一个任务后，主管继续派第二个任务；员工复用原会话，能利用前一个任务的上下文。
3. 用户显式要求“任务交给某员工”，主管必须按原参数派发，不能因为该员工正忙或主管认为其他人更合适而改派。
4. 用户给离线节点上的员工派任务或创建员工，系统立即报错，不产生任务或员工记录，用户可换节点或等待。
5. 任务执行期间主管电脑关机；节点完成任务后结果保存在节点事件日志；主管会话重新启动后，用户查询结果，完整结果只注入一次并能继续追加任务。
6. 任务执行失败，主管收到失败报告，系统不自动重试；用户或主管显式新建任务后才重新执行。
7. 用户显式取消正在执行的任务，节点代理终止 pi 进程树，任务进入 `canceled`。
8. 员工机注销导致任务中断，重新登录后节点代理补报 `interrupted`，不自动续跑。
9. 同一节点创建第二个员工时，如果工作目录与第一个员工相同，立即拒绝。
10. 主管无法读取员工机器上的任意文件；只能查看任务状态和员工提交的结果报告。

## 9. 会话能力验证结果

**验证时间**：2026-10-22

**环境**：

- Claude Code 2.1.304
- pi 1.3.0
- 本机 Windows

**方法**：

- 为每个 harness 生成固定 session id；
- 第一轮发送“记住暗号 ORCHID-731”；
- 进程退出后，第二轮使用同一个 session id 恢复，询问暗号；
- 两轮均为独立进程，不使用工具。

**结果**：

| Harness | 第一轮 | 第二轮（恢复） | 结论 |
|---|---|---|---|
| Claude Code | `OK` | `ORCHID-731` | 跨进程会话恢复通过 |
| pi | `OK` | `ORCHID-731` | 跨进程会话恢复通过 |

**备注**：

- Claude Code 本机配置输出过 `unrecognized_model` 提示（自定义模型配置），但会话恢复行为正常。
- pi 首次使用新 session id 时会提示创建新会话，符合预期。

**尚未验证**：

- Claude Code 接入 MCP 管理工具后的实际工具调用；
- pi 在带工具、带工作目录执行任务时的会话连续性；
- 取消任务时的进程树终止；
- 长会话、上下文压缩后的会话连续性；
- 同一节点多个员工并发的资源与稳定性；
- 主管端与节点代理跨进程通信的断线重连和补报。

## 11. 实现与验证状态

**更新时间**：2026-10-22

### 已实现

- 节点代理：HTTP API、Bearer token 鉴权、zod 请求校验、工作目录白名单、SQLite 持久化、FIFO 调度、单员工单运行任务。

- 主管端：节点配置、在线状态缓存、员工/任务/事件同步、离线缓存回退、结果投递与事件确认。
- MCP：11 个管理工具，主管规则写入工具描述与 `CLAUDE.md`。
- 上下文治理：`list_tasks`、`get_task`、`list_pending_results` 等输出不含结果全文；只有 `get_task_result` 注入全文并完成投递确认。

### 实现决策与差异

- pi 提示通过 stdin 传入，避免 Windows 命令行长度限制；结果从最后一个 `turn_end` 的 assistant 文本块提取。
- 工作目录通过 `allowedRoots` 解析并校验，节点内以规范化路径保证唯一。
- 主管端缓存只用于节点离线时的读取回退；节点在线时以节点数据为准。
- 事件在结果被 `get_task_result` 完整读取后才标记投递并回传确认，避免结果丢失。
- 员工停用为终态，当前不提供重新启用。
- “显式指定员工不可改派”目前由 MCP 工具契约和主管提示词约束，不是服务端强制策略。
